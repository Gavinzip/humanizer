# 繁體中文編輯

處理繁中正文、投影片文字或口頭講稿時讀取。技術術語和使用者要求的語域優先；英文模式清單中的大小寫、引號與連字號規則不能直接套用到中文。

## 先決定這段話要怎麼被讀

| 用途 | 編輯方向 |
|---|---|
| 論文、研究摘要、技術文件 | 保留術語、限定條件和引用，清掉空泛評價與繞句 |
| 現場報告、口頭解釋 | 按聽眾理解順序拆開長句；保留必要的指圖、轉場與停頓 |
| 信件、工作說明 | 清楚交代主詞、動作、對象和需要對方處理的事 |
| 個人文章、社群貼文 | 保留作者已有的情緒、節奏與用詞，不另加人設 |

「口語」不等於每句加「其實」「啦」「對吧」，也不要求故意寫錯或把術語全部換成日常比喻。論文摘要轉成報告講稿時，精確度不變，解釋的順序和句子可以改。

## 從作者的原句開始

先讀作者怎麼把事情接著說下去，再判斷哪裡需要修。正式用詞與一般說話方式可以自然並存，不必把整段統一成公文或聊天口吻。「去做」「這個部分」「先確認一下」是否保留，要看它在句子裡的語氣和作用；不能只因為刪掉後更短，就一律當成贅詞。

潤稿先保留原有句型，只修不清楚或不合用途的部分。長句裡的幾個步驟若接得清楚，可以維持連寫；不要為了看起來口語就拆成問句。原句已經適合用途時可以不改。使用者要求重寫、重整或改成口頭講稿時，再依該任務調整幅度。

不要把上述詞組當成新的自然感配方。「應該」「需要」「可以」各有立場和責任上的差別，不能為了模仿語氣隨意增刪。已確認偏好來自目前使用者的 profile；如何學習回饋見 [feedback-learning.md](feedback-learning.md)，樣本歸屬依 [speaker-voice.md](speaker-voice.md) 處理。

## 對話與日常說明

當這份 skill 用來調整對話回覆時，依對方這一輪要知道的事情決定篇幅。先接住已知的問題，再補理解或決策需要的理由；不必每次重新定義背景、宣布分析步驟，再把答案整理成完整報告。查證、比較或多步操作仍可用表格與條列。

讓前後句的關係清楚：一句交代情況，後一句接原因、限制或接下來要做的事。不要把每句都切短，也不要每段都做出一句可單獨摘錄的結論。訊息已說完時就停，不加沒有新資訊的收尾。

回覆本身也要照這個方式寫。簡單問題直接回答，不固定加上粗體判語、幾點分析，再教使用者「真正重要的是什麼」。像「這也讓我們的方向更清楚」「這個差別更值得留意」這類句子，若只是在評論對話本身就刪掉；需要提醒意思改變時，直接指出哪個詞改變了什麼意思。必要的限制講一次即可，不用每次重講整套背景。

台灣用語之外，也要檢查是否留下翻譯式語序與抽象名詞堆疊。依原稿找回誰做什麼；不為了變口語而省掉責任、期限或限制。聊天訊息裡的錯字、空格和斷句不直接視為作者想保留的風格。

需要一起試調語氣時，依 [speaker-voice.md](speaker-voice.md) 的回饋流程進行。讀者覺得自然與否，以實際試稿回饋確認；不用偵測器分數或刻意增加不規則性代替這項判斷。

外部偵測由 [detector-checks.md](detector-checks.md) 處理，須先有使用者對服務與提交範圍的授權。分數不替代本人對文章的回饋，也不把通過的版本自動變成個人語氣樣本。

## 用語、標點與文件結構

- 繁中未另指定地區時，使用台灣常用語，例如軟體、影片、網路。不要機械替換專有名詞、原文引述，或在領域中有特定意思的「數據」「模型」等詞。
- 中文正文使用全形標點；一般引述用「」，內層用『』。精確引用的內容、程式碼、網址、識別字和來源標題保持原樣。
- 區間、負號和公式有各自意義；`2021–2024`、`−0.2`、`95% CI` 不能當成西化標點清除。
- 修辭性的破折號、冒號和分號，要檢查是否真的表達插入、引出或並列；不要只把一種符號全部換成另一種。
- 純潤稿保留真正的標題、條列、表格和投影片位置。若使用者要求重整結構，再調整組織方式，並保留資料與引用的對應。

## 常見問題與判準

| 現象 | 要檢查什麼 | 修法 |
|---|---|---|
| 「彰顯」「賦能」「深刻體現」 | 後面是否說了可辨識的事情 | 改成原文支持的動作或結果；沒有具體資料就保持簡單 |
| 「進行……的建構」「達成……的實現」 | 名詞化是否把動作藏起來 | 找回誰做什麼，必要時拆句 |
| 每段都「此外」「值得注意的是」 | 真的有新增或轉折嗎 | 刪掉無功能的預告；保留有邏輯作用的連接詞 |
| 每頁三點、每句對仗 | 分組是否由內容決定 | 依內容保留合理數量，不湊齊形式 |
| 「不是 X，而是 Y」 | 是否在糾正真實存在的誤解 | 真正的概念辨別保留，空造對手的金句改直述 |
| 「其」「此」「該」連用 | 聽眾是否能辨認指的是誰 | 直接寫必要的對象；不為求變化反覆換術語 |
| 「顯著提升」「充分證明」 | 原文是否有對應統計或論證 | 保留原文有根據的強度；不能把「可能」修成「確定」 |
| 自嘲、生活細節、個人經歷 | 是否出現在作者素材裡 | 有就保留適量；沒有就不要補來製造真人感 |

## 編輯尺度範例

下列都是編輯用的虛構素材，不是研究結果。改稿只能使用同一列原稿已給的資訊。

| 原稿 | 改稿 | 保住的意思 |
|---|---|---|
| 上線之前，需要先去確認付款和配送設定，測試訂單也要跟正式訂單分開。 | 保留原句。 | 工作要求已清楚；「先去確認」不必只為縮短而刪字 |
| 透過對兩組結果進行比較，我們得以發現 A 組所需時間較 B 組更短。 | 比較兩組結果後，可以看到 A 組花的時間比較短。 | 組別、指標和方向；沒有新增原因或幅度 |
| 值得注意的是，此實驗僅納入 24 位參與者，因此尚無法確認結果是否適用於其他族群。 | 這個實驗只有 24 位參與者，結果能不能用在其他族群，還不能確定。 | 樣本數和適用範圍；口語化沒有增加確定性 |
| 本次報告旨在深入探討兩種方法在電腦記憶體使用量上的差異。 | 這次報告比較兩種方法用了多少記憶體。 | 保留比較的指標，沒有新增哪個方法比較好的結論 |

若原稿只有「本系統大幅提升效能」，不能改成「延遲減半」。可寫「原稿宣稱系統效能提升，但未提供指標或幅度」，或在審稿意見標出資料缺口。依任務保留未證實狀態，不把猜測混入成稿。

## 完稿檢查

逐句核對數字、對象、比較基準和限定語，尤其檢查「可能」「只在」「尚未」「相關」是否被刪掉。再看是否把自然的中文修成齊整口號、添加語助詞，或把技術詞換成更難懂的比喻。

最後對照作者原稿：有沒有只為換字而改掉原有說法，或把每段都整理成「提出問題 → 解釋 → 提醒」？段落本來就有清楚順序時不必刻意打散；需要修的是不合內容的套版，也不靠製造凌亂來模仿真人。

只交付使用者要的改稿或審稿意見；不固定輸出「初稿／去 AI 分析／終稿」三份文字。
